Where these builds actually break

A green checkmark on an empty payload

The HTTP Request node pulls raw page source. On a page that renders its content client side, the source it pulls is the shell, and the data was never in it. The node does not error. The Code node cleans nothing. The model dutifully analyzes nothing. The execution log shows a clean run.

This is the failure that survives a demo and shows up three weeks later when someone finally checks the export against the site.

Fix: render capable fetch, plus a row count assertion that fails the run loudly instead of exporting silence.

Your instructions billed once per record

Every node in n8n runs once per input item by default. Hand the model node 400 records and you have bought 400 calls. The record data is small. The instruction block riding along on each of those calls is not.

At normal record counts the instructions, not the data, are the majority of the bill. The workflow looks identical on the canvas either way.

Fix: gate junk before the model, group records into batches, send the instruction block once per batch.

What this prototype is and is not

  • The failure modes are real. Client side rendering returning an empty shell to a plain HTTP fetch, and per item execution multiplying a fixed instruction block, are both documented n8n behaviors, not projections.
  • The volumes are sample data. Nothing here touches your sources. Record counts, token sizes, and yield rates are set to plausible defaults so the shape of the math is visible.
  • Input tokens only. Output token cost is excluded. Including it widens the gap between the lanes, it does not narrow it.
  • The model rate is yours to set. The dial is a slider, not a quoted price. Set it to whatever your account actually pays.
  • Instruction block modeled at 850 tokens, record payload at 220. Long instructions push Lane A worse. Short ones pull it closer. The crossover is far below any realistic prompt.
  • Batch size fixed at 25 records per call. Real batch size depends on record width and the model context you are targeting. It is a tuning decision, not a constant.
  • What this does not show. Retry and error branch behavior, source specific rate limits, or export schema validation. Those are build decisions, not calculator inputs.
